# D58. One relational state layer

## Context

No control had a pressed state and only inputs had disabled. Shell links and option items painted selected with the same fill as hover, `--bg-hover` was a fixed color pair that doubled as selected, and hover wasn't gated by `(hover: hover)`, so it stuck after a tap on a touch screen. D33 had approved interaction presets as plans, with no content yet.

## Options considered

Weighed at the time, on a decision card in the plan: one relational layer, where each control mixes its own ink into its own fill by a share; the same layer painted by a pseudo-element, as a state layer often is (rejected: `::before` is the touch hit area and `::after` the card edge and the tab's mark); or fixed colors added per primitive, state by state (fast, not relational, and the drift returns).

## Decision

One relational layer. Three knobs (`--state-hover` 6%, `--state-press` 12%, `--state-selected` 10%) set the share; each control paints `color-mix(its ink, its fill)` by that share, through two registered percentages (`--state-act`, `--state-on`) that don't inherit, so a hovered row doesn't hover the button inside it. Hover sits inside `(hover: hover)`. Selected keeps a mark of its own. Disabled drops hover and press. Focus stays one ring. `.u-state` gives a control of your own the same layer, which the owner asked for: custom interactions should be easy.

## Consequences

D33's first concrete content. `--bg-hover` no longer paints hover in core and stays one minor. A product that wants softer or stronger states turns three knobs. The switch (D59) takes the same layer on its track.
