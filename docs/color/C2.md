# C2 Light and dark

## What it is

Every role is a pair: a light form and a dark form, written once as `light-dark(light, dark)`. Which one paints is decided by the `color-scheme` of the element being painted. The root follows the system unless `data-theme` names one:

| Root | `color-scheme` | Paints |
|---|---|---|
| no `data-theme` | `light dark` | the system's choice |
| `data-theme="light"` | `light` | the light forms |
| `data-theme="dark"` | `dark` | the dark forms |

The two forms are not two palettes. A neutral role steps along one lightness ladder in each theme, so the page, a raised surface and ink keep their order and their distance. A hue (the accent, a kind, a status) is its seed in the light theme and the same color lifted by `--color-lift` (0.17 of OKLCH lightness) in the dark, so it keeps its hue and chroma and stays readable on a dark page. Ink on a fill is recomputed in each theme from that theme's fill, which is why the accent's ink is white in light and a dark blue in dark.

## Why

Two hand-set palettes drift: a role gets a new light value and its dark value is forgotten. One declaration per role cannot drift, and deriving the dark form from the light seed means a product chooses each color once. The lift is one number because the failure it prevents is one failure: a hue tuned for a light page goes muddy on a dark one.

## How it is computed, in plain words

- `light-dark()` is not resolved where a role is declared. A role on the root holds both forms, and each element that paints with it picks the form for its own `color-scheme`. So a box can set `color-scheme: dark` and every role inside it turns dark, with no other change. The specimen's Color section draws each role as a light and dark pair this way: two cards, each with its own scheme, reading the same tokens.
- The seeds are read on the root. A role's seed is substituted where the role is declared, so a box that sets `--seed-accent` does not recolor the accent inside it. To recolor a part of a page, set the role there instead.
- `--lift` (the shadow of a raised float) is a pair too: a soft gray in light, a deeper black in dark, where a light shadow would not show.
- A browser without relative colors gets the same roles as fixed hex pairs, still inside `light-dark()`, so both themes work. Those values come from `math.js` at the default seeds; a product's own seeds there fall back to core's palette.

## Where it lives in the code

- `core.css`, `@layer trellis.theme`: `color-scheme` on `:root` and its two `data-theme` forms; every role's `light-dark()`; the `@supports not (color: oklch(from red l c h))` fallback.
- `tokens.json`: each neutral role's `light` and `dark` lightness, and `color.lift`.
- `math.js`: `palette('light' | 'dark', seed)`, and `hue()` for the lift.

## How it is checked

`tests/contract.js` runs every contrast floor in both themes ([C4](C4.md)). `tests/matrix.js` runs `tests/align.js` across light and dark, so nothing moves off its line when the theme turns. A scheme set on part of a page, as a supported pattern with its own class, is a planned item and is not in core yet.
